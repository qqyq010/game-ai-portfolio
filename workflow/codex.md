# Codex와 작업하는 방식

Codex Desktop에서 프로젝트를 열고 Markdown에 목표와 완료 조건부터 적습니다. Obsidian에서 계획을 읽으며 먼저 손볼 것과 팀원이 맡은 부분을 구분합니다. Coin Survivor에서는 그 과정에서 합성을 미루고 아이템을 집고 놓는 조작부터 다듬기로 했습니다. [실제로 작업을 좁힌 사례](../projects/coin-survivor/inventory-pick-and-place.md)

## 버그를 만났을 때

1. 재현 순서, 기대한 동작, 실제 화면을 적고 로그나 화면을 붙입니다.
2. 바로 고치기 전에 코드를 읽고 원인 후보와 근거를 정리해 달라고 합니다.
3. 설명을 보고 고칠 파일과 팀원이 맡은 코드를 구분해 수정을 맡깁니다.
4. 빌드 결과를 보고 같은 순서로 Unity Play Mode에서 직접 확인합니다. 실행해 본 범위는 따로 남깁니다.
5. 처음 요청과 변경 파일, 확인 기록을 꺼내 요구별 결과를 다시 봅니다. [quality-pass 적용 방법](quality-pass/README.md)

## 반복해서 설명하던 건 작업 방법으로 남겼습니다

여러 프로젝트에 적용할 원칙은 공통 지침에 두고, 프로젝트의 수정 범위는 그 프로젝트 문서에 적었습니다. 다음 작업에서 다시 필요한 선호는 Memory에 두었습니다. 회의 전사를 만들고 빠진 결정을 확인하는 순서는 Skill로 정리했습니다. [회의에서 빠진 안건을 복원한 과정](team-notes.md)

새 검색 방식을 검토할 때도 지금 필요한 일을 먼저 정했습니다. 못 찾던 기록을 더 찾는지, 엉뚱한 결과가 늘었는지 보고 적용할 범위를 골랐습니다. [검색 도구 검토](search-review.md)

## 일을 나눴다가 한 대화로 돌아온 이유

지침을 비교할 때는 사례 작성, 버전별 검토, 결과 비교의 역할을 나눴습니다. 개선판인지 가려 비교했지만 두 번의 비교에서 판단 차이를 확인하지 못했습니다. 같은 모델 계열의 검토 결과였으며, 비교에서 실제로 확인된 분류 변화만 남겼습니다.

긴 자료 조사에서는 Goal로 수집부터 재분석까지 단계와 원문 위치를 적었습니다. 보조 작업을 나눴을 때 제가 끝까지 원문을 대조한 자료가 기대만큼 늘지 않아 한 대화로 돌아갔습니다. 이후에는 맡긴 작업의 수보다 제가 확인을 끝낸 결과와 그 과정에 든 시간을 먼저 보고 싶습니다.
